# CI 发版正文组装：后步覆盖前步，手动说明静默丢失

多步 CI 发布流水线向同一个 Release（或任何发布产物元数据）先后写入内容时的组装纪律。适用于 GitHub Releases / GitLab Release / 自建发布系统。

## 背景

发布链常由多个 step 依次完善同一个发布对象：创建（手动说明 + changelog）→ 补充（平台构建状态 / 资产清单）→ 校验。每一步都「正确地」写了自己的内容，组合起来却会互相覆盖。

## 决策或坑

1. **后步整段覆盖前步**——创建步写入「手动说明 + changelog」，后续「更新正文」步用 `release edit --notes` 只写「changelog + 构建状态」→ 手动说明被整段冲掉，**无任何报错**，发布显示为成功。
2. **dispatch 手动输入（release_notes / 人工说明）是流水线里最容易被丢弃的内容**——它只在创建步被消费，后续步骤各自拼装时不会带上它。
3. **多步写同一产物没有单一组装点**——每个 step 各自拼 body，内容此消彼长，谁后写谁生效。

## 通用原则

1. **同一产物的多步写入必须「读-合-写」或单点组装**：后步编辑前先取现值合并自己的增量；或把全部内容要素（手动说明、changelog、状态）传入每一步做完整组装——禁止只写自己的增量。
2. **手动输入是最高优先级内容**：dispatch 参数 / 人工说明必须一路透传到最终写点，任何自动化步骤不得丢弃。
3. **发布链最后加正文断言**：校验关键章节/关键词存在（如功能清单、更新内容），丢内容 = 构建失败——正文覆盖是静默失败，只有断言能兜住。

> **注（GitHub Actions 写法）**：
> - 各步 body 组装统一为 `手动说明 + changelog + 各步增量`，`gh release edit` 时重复带上全部要素
> - 断言步：取 release body，`grep` 关键章节，缺失则 `exit 1`

## 适用范围

任何「多步组装发布说明」的 CI 发布链。单步创建发布、正文一次性写完的场景不涉及。
