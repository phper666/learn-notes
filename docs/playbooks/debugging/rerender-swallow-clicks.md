# 高频重渲染吞点击：按钮「看得见、点了没反应」

轮询/推送驱动重渲染的 UI（桌面壳设置页、监控仪表盘）中，交互按钮时灵时不灵的排障与防御。

## 背景

设置类页面常用固定间隔（如 250ms）轮询状态并整块重渲染。渲染函数若「无条件 innerHTML 重建 + 逐次绑定事件」，按钮 DOM 节点每秒被替换数次。

## 决策或坑

1. **重建吞点击**——mousedown 与 click 之间节点被替换，click 事件落在已脱离文档的旧节点上，监听器收不到 → 「按钮看起来在、点了没反应」，偶发能点中（落进两次重建的间隙）表现为时灵时不灵、无任何报错。
2. **逐渲染绑定监听器 = 节点一换监听即丢**——`innerHTML` 重建后重新 `addEventListener` 的写法，在高频重渲染下等于没有绑定。
3. **纯数据守卫不够**——「数据没变不重建」只在数据稳定时有效；进度类场景数据每帧都变，重建无法避免，可点击元素的稳定性必须另靠事件绑定方式保证。

## 通用原则

1. **会重建的容器，事件一律委托**：在静态父容器上绑定一次监听，`closest('button')` 按标识分发动作——节点重建不影响监听。
2. **渲染函数内禁止出现 addEventListener**：绑定只发生在初始化阶段；渲染只负责 HTML/数据。
3. **变更守卫仍值得做**（数据 key 没变跳过重建）：省渲染、防滚动位置/输入焦点丢失，但要认清它不解决高频变化场景的点击问题。
4. **排障线索**：「元素静态可见 + 点击时灵时不灵 + 无报错」→ 先查该节点是否被高频替换（DevTools 对比前后节点引用是否同一对象）。

## 适用范围

轮询/推送驱动的重渲染 UI。一次性渲染、静态页面不涉及。
