# 自更新链路新项目接入顺序（runbook）

新项目从零打通「打包 → 签名 → 发布 → 自动更新」的执行顺序清单。各坑的机理详见对应 playbook（见每步的「依据」），本文件只管**顺序**——顺序错了，坑会以更贵的代价出现（如：先发了无签名版本，存量用户就永远救不回来）。

## 背景

签名/自动更新的坑多数是「单向门」或「静默失败」：事后补救代价远高于事前顺序正确。本 runbook 把分散在各 playbook 的原则按时间轴排成一条线。

## 接入顺序（首发前全部完成）

1. **定签名方案（不可逆，最先定）**
   - 依据：macos-code-signing 原则 2/9
   - 决策点：付费 Developer ID + 公证（首装体验无损）/ 自签名证书（零成本，自更新无损但首装有 Gatekeeper 摩擦）/ 无签名（自更新链直接残废，禁选）
   - 一旦有用户装机，方案即锁定；切换 = 全量手动重装

2. **签发证书并异机备份（紧跟方案）**
   - 依据：macos-code-signing 原则 3
   - 证书文件 + 密码 + 注入方式（secret 名）登记到密钥目录；证书即升级生命线

3. **打包配置（含产物命名）**
   - 依据：electron-crossplatform 原则 2/3/6
   - 更新源与打包器 publish 严格一致；mac target 含 zip；**产物名硬编码连字符（禁空格）**；捆绑运行时 per-platform 映射

4. **CI 签名流水线（五步）+ 双门禁**
   - 依据：macos-code-signing 原则 1/4 + 注
   - 五步流水线 + `forceCodeSigning` 门禁（不显式写 identity）+ 产物 `codesign --verify` 验签步

5. **更新器基线（首发就带上，别等踩坑）**
   - 依据：macos-code-signing 原则 7/8
   - 更新器内部日志接入应用日志；差分基缓存对账（下载记版本 / 启动对账不一致清基）

6. **发布链正文组装纪律**
   - 依据：release-body-overwrite 全文
   - 手动说明透传到最终写点；多步写入读-合-写；发布链末尾正文关键内容断言

7. **首版发布 = 冒烟测试**
   - 首个版本发布后立即实测完整链路：下载产物验签 → 干净机器安装 → 应用内检查更新 → 升级到下一版
   - 首版就带真实签名——首版无签名，存量永远救不回（原则 2/9）

## 已知边界（知识覆盖不到的）

- **Windows 签名**（SmartScreen / EV vs OV 证书）与 **notarize 公证**流程未沉淀（未踩过）
- **工具版本漂移**：electron-updater/electron-builder 大版本升级后，具体 flag 以「注」为准需复测，原则不变

## 来源

出生：dsh-hull-desktop v0.1.0~v0.1.8 全链路实测（2026-08-25~30）——顺序即代价：无签名首发 → 存量不可救 → 手动迁移。2026-08-30 抽象为 runbook。
